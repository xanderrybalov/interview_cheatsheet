01 Node.js / Backend

package.json

Манифест проекта. Три ключевые роли: зависимости (dependencies — прод, devDependencies — только разработка), скрипты (scripts — точки входа: start, build, test, lint), метаданные (версия, имя, engines — минимальная версия Node).

package-lock.json — фиксирует точные версии всего дерева зависимостей для воспроизводимых сборок.

package.json

Project manifest. Three key roles: dependencies (dependencies — production, devDependencies — dev only), scripts (scripts — entry points: start, build, test, lint), metadata (version, name, engines — minimum Node version).

package-lock.json — locks exact versions of the entire dependency tree for reproducible builds.

Event Loop

Event loop — механизм, позволяющий однопоточному Node.js делать неблокирующий I/O.

Алгоритм работы:

  1. Берёт и выполняет весь синхронный код из Call Stack
  2. Проверяет очередь микротасков — выполняет все до единого
  3. Берёт одну задачу из очереди макротасков и выполняет
  4. Возвращается к шагу 2 (снова проверяет микротаски)
  5. Цикл повторяется пока есть задачи

Event Loop

Event loop — the mechanism that allows single-threaded Node.js to perform non-blocking I/O.

How it works:

  1. Takes and executes all synchronous code from the Call Stack
  2. Checks the microtask queue — executes all of them
  3. Takes one task from the macrotask queue and executes it
  4. Returns to step 2 (checks microtasks again)
  5. Repeats while there are pending tasks

Порядок выполнения кода

1) Синхронный код (Call Stack) — выполняется немедленно

2) Microtasks — сразу после синхронного кода (и после каждого макротаска):

  • process.nextTick() — высший приоритет среди микро
  • Promise.then / catch / finally
  • queueMicrotask()

3) Macrotasks — берутся по одной, между ними всегда проверяются микротаски:

  • setTimeout / setInterval
  • setImmediate (в Node.js)
  • I/O операции (файл, сеть)
  • UI рендеринг

Code Execution Order

1) Synchronous code (Call Stack) — executed immediately

2) Microtasks — right after sync code (and after each macrotask):

  • process.nextTick() — highest priority among microtasks
  • Promise.then / catch / finally
  • queueMicrotask()

3) Macrotasks — taken one at a time, microtasks always checked in between:

  • setTimeout / setInterval
  • setImmediate (Node.js)
  • I/O operations (file, network)
  • UI rendering

Нюансы Promise

Promise.resolve() создаёт уже выполненный промис, но .then колбэк всё равно уходит в очередь микротасков — не выполнится синхронно.

new Promise(executor) — executor выполняется синхронно. Только .then уходит в микротаски.

console.log('1');                   // sync → 1
new Promise(resolve => {
  console.log('2');                 // sync → 2 (executor!)
  resolve();
}).then(() => console.log('3'));    // micro → 4
console.log('4');                   // sync → 3
// Вывод: 1, 2, 4, 3

Полный пример:

console.log('1');                   // sync → 1
setTimeout(() => console.log('2'), 0);  // macro → 5
setImmediate(() => console.log('3'));   // macro → 6
Promise.resolve().then(() =>
  console.log('4'));                // micro → 3
process.nextTick(() =>
  console.log('5'));                // micro (!) → 2
console.log('6');                   // sync → 4
// Вывод: 1, 6, 5, 4, 2, 3

Promise Nuances

Promise.resolve() creates an already resolved promise, but the .then callback still goes to the microtask queue — it won't execute synchronously.

new Promise(executor) — the executor runs synchronously. Only .then goes to microtasks.

console.log('1');                   // sync → 1
new Promise(resolve => {
  console.log('2');                 // sync → 2 (executor!)
  resolve();
}).then(() => console.log('3'));    // micro → 4
console.log('4');                   // sync → 3
// Output: 1, 2, 4, 3

Full example:

console.log('1');                   // sync → 1
setTimeout(() => console.log('2'), 0);  // macro → 5
setImmediate(() => console.log('3'));   // macro → 6
Promise.resolve().then(() =>
  console.log('4'));                // micro → 3
process.nextTick(() =>
  console.log('5'));                // micro (!) → 2
console.log('6');                   // sync → 4
// Output: 1, 6, 5, 4, 2, 3

Асинхронность

Callback — функция, которую мы передаём как аргумент, чтобы она вызвалась позже (когда завершится операция). Базовый механизм асинхронности в Node.js.

fs.readFile('data.json', (err, data) => {
  // колбэк вызовется когда файл прочитан
});

Callback hell — вложенные колбэки, нечитаемо, сложно обработать ошибки:

getUser(id, (user) => {
  getOrders(user, (orders) => {
    getDetails(orders[0], (d) => { ... })
  })
})

Promise — обёртка над будущим результатом. Три состояния: pending → fulfilled / rejected. Цепочка .then() линеаризует код, .catch() централизует обработку ошибок.

async/await — синтаксический сахар над Promise. async функция всегда возвращает Promise. await приостанавливает выполнение функции (не потока!) до резолва.

async function getOrderDetails(id) {
  const user = await getUser(id);
  const orders = await getOrders(user);
  return getDetails(orders[0]);
}

Параллельность: Promise.all([a(), b()]) — запускаем независимые задачи параллельно, а не последовательно.

Asynchrony

Callback — a function passed as an argument to be invoked later (when an operation completes). The foundational async mechanism in Node.js.

fs.readFile('data.json', (err, data) => {
  // this callback fires when file is read
});

Callback hell — deeply nested callbacks, unreadable, hard to handle errors:

getUser(id, (user) => {
  getOrders(user, (orders) => {
    getDetails(orders[0], (d) => { ... })
  })
})

Promise — a wrapper around a future result. Three states: pending → fulfilled / rejected. Chaining .then() linearizes code, .catch() centralizes error handling.

async/await — syntactic sugar over Promises. An async function always returns a Promise. await pauses function execution (not the thread!) until resolution.

async function getOrderDetails(id) {
  const user = await getUser(id);
  const orders = await getOrders(user);
  return getDetails(orders[0]);
}

Concurrency: Promise.all([a(), b()]) — run independent tasks in parallel instead of sequentially.

02 React / Frontend

Компоненты

Функциональные — стандарт. Просто функция, возвращающая JSX. Состояние и сайд-эффекты через хуки (useState, useEffect, useMemo).

Классовые — легаси. render(), lifecycle методы (componentDidMount, shouldComponentUpdate). Используются если проект старый или нужны Error Boundaries.

Как синьор: классы — только в legacy. Новый код — только функциональные.

Components

Functional — the standard. Just a function returning JSX. State and side effects via hooks (useState, useEffect, useMemo).

Class-based — legacy. render(), lifecycle methods (componentDidMount, shouldComponentUpdate). Used in old projects or for Error Boundaries.

Senior take: classes only in legacy code. All new code — functional only.

Для глобального состояния: Context API (простое), Redux/Zustand (сложное).

Data flow — unidirectional. Data flows top-down via props. Child affects parent through callback props.

For global state: Context API (simple), Redux/Zustand (complex).

Controlled vs Uncontrolled

Controlled — React владеет значением инпута. Значение живёт в state, обновляется через onChange. Полный контроль: валидация на лету, условная логика.

const [email, setEmail] = useState('');
<input value={email}
  onChange={e => setEmail(e.target.value)} />

Uncontrolled — DOM владеет значением. Читаем через ref при submit. Проще для простых форм, file inputs.

const ref = useRef();
<input ref={ref} />
// ref.current.value при submit

Как синьор: по умолчанию — controlled. Uncontrolled — только для file input или интеграции с non-React библиотеками.

Controlled vs Uncontrolled

Controlled — React owns the input value. Value lives in state, updated via onChange. Full control: on-the-fly validation, conditional logic.

const [email, setEmail] = useState('');
<input value={email}
  onChange={e => setEmail(e.target.value)} />

Uncontrolled — DOM owns the value. Read via ref on submit. Simpler for basic forms, file inputs.

const ref = useRef();
<input ref={ref} />
// ref.current.value on submit

Senior take: controlled by default. Uncontrolled only for file inputs or non-React library integration.

03 TypeScript

Способы объявления типов

  • type — для union-типов, примитивов, утилит. type Status = 'active' | 'inactive'
  • interface — для объектов и классов. Поддерживает extends и declaration merging.
  • enum — набор констант. Предпочитаю as const объекты (tree-shakeable).
  • Generics — параметризация: function get<T>(arr: T[]): T

Type Declaration Methods

  • type — for unions, primitives, utilities. type Status = 'active' | 'inactive'
  • interface — for objects and classes. Supports extends and declaration merging.
  • enum — constant set. I prefer as const objects (tree-shakeable).
  • Generics — parameterization: function get<T>(arr: T[]): T

Почему TypeScript

  1. Safety — ошибки на этапе компиляции, а не в продакшене. Невозможно вызвать user.nmae — тайпчекер поймает.
  2. DX — автокомплит, рефакторинг с уверенностью (переименовал поле — IDE покажет все места), самодокументирующийся код.
  3. Масштабируемость — контракты между модулями/командами. Новый разработчик читает типы вместо документации.

Кратко: TypeScript — инвестиция в поддерживаемость. На маленьком проекте overhead, на большом — спасает.

Why TypeScript

  1. Safety — errors caught at compile time, not in production. Can't call user.nmae — type checker catches it.
  2. DX — autocomplete, confident refactoring (rename a field — IDE shows every usage), self-documenting code.
  3. Scalability — contracts between modules/teams. New devs read types instead of documentation.

In short: TypeScript is an investment in maintainability. Overhead on small projects, lifesaver on large ones.

Iterators и Generators

Iterator — объект с методом __next__(). Лениво выдаёт элементы по одному. Любой for в Python работает через итераторы.

Generator — функция с yield вместо return. При вызове возвращает iterator, не выполняясь. Каждый next() выполняет код до следующего yield.

def read_huge_file(path):
    with open(path) as f:
        for line in f:
            yield line.strip()
# в памяти одна строка, не весь файл

Lazy evaluation — вычисляем значения только когда нужны.

Когда генераторы дают выигрыш:

  • Большие файлы / потоки (не грузим всё в RAM)
  • Пайплайны трансформаций
  • Бесконечные последовательности (IDs, пагинация)
  • ETL-процессы

Iterators & Generators

Iterator — an object with a __next__() method. Lazily yields elements one by one. Every for loop in Python works through iterators.

Generator — a function with yield instead of return. Calling it returns an iterator without executing. Each next() runs code until the next yield.

def read_huge_file(path):
    with open(path) as f:
        for line in f:
            yield line.strip()
# only one line in memory, not the whole file

Lazy evaluation — compute values only when needed.

When generators win:

  • Large files / streams (don't load everything into RAM)
  • Transformation pipelines
  • Infinite sequences (IDs, pagination)
  • ETL processes

06 Дизайн БД / Database Design

Нормализация — уровни

Каждая следующая нормальная форма включает все предыдущие.

1NF — Атомарность
Каждая ячейка — одно значение, нет повторяющихся групп.
✗ phones: "+380..., +380..."
✓ Отдельная таблица user_phones

2NF — Нет частичных зависимостей
Неключевой атрибут зависит от всего составного ключа.
✗ product_name зависит только от product_id, не от (order_id, product_id)
✓ Выносим в таблицу products

3NF — Нет транзитивных зависимостей
Неключевой атрибут не зависит от другого неключевого.
✗ department_name зависит от department_id, не от PK
✓ Выносим в таблицу departments

BCNF — каждый детерминант — кандидат в ключи. Редко отличается от 3NF.

4NF — нет многозначных зависимостей. Два независимых набора связей → отдельные таблицы.

На практике: доводим до 3NF (стандарт OLTP), дальше — только при конкретных аномалиях.

Normalization Levels

Each successive normal form includes all previous ones.

1NF — Atomicity
Every cell holds a single value, no repeating groups.
✗ phones: "+380..., +380..."
✓ Separate user_phones table

2NF — No partial dependencies
Non-key attribute depends on the entire composite key.
✗ product_name depends only on product_id, not on (order_id, product_id)
✓ Move to products table

3NF — No transitive dependencies
Non-key attribute doesn't depend on another non-key attribute.
✗ department_name depends on department_id, not on PK
✓ Move to departments table

BCNF — every determinant is a candidate key. Rarely differs from 3NF.

4NF — no multi-valued dependencies. Two independent relationship sets → separate tables.

In practice: normalize to 3NF (OLTP standard), go further only for specific anomalies.

Денормализация

Намеренно дублируем данные для скорости чтения.

  • + Быстрые запросы без JOIN, проще агрегации
  • − Дублирование, риск рассинхрона, сложнее обновлять

Типичные приёмы: order_total в таблице заказов, user_name рядом с комментарием, materialized views.

OLTP → нормализация. OLAP → денормализация. На практике — гибрид.

Denormalization

Intentionally duplicate data for read performance.

  • + Fast queries without JOINs, simpler aggregations
  • − Duplication, sync risk, harder to update

Common techniques: order_total in orders table, user_name alongside comments, materialized views.

OLTP → normalize. OLAP → denormalize. In practice — hybrid.

Связи

  • 1:1 — user ↔ profile (разделение горячих/холодных данных)
  • 1:N — user → orders (FK в таблице orders)
  • M:N — products ↔ categories (junction table product_categories)

Проектирование — подход

  1. Определить сущности и атрибуты
  2. Определить связи и кардинальность
  3. Нормализовать до 3NF
  4. Денормализовать точечно под нагрузку (по профилированию, не заранее)
  5. Индексы — на поля WHERE, JOIN, ORDER BY

Relationships

  • 1:1 — user ↔ profile (hot/cold data separation)
  • 1:N — user → orders (FK in orders table)
  • M:N — products ↔ categories (junction table product_categories)

Design Approach

  1. Identify entities and attributes
  2. Define relationships and cardinality
  3. Normalize to 3NF
  4. Denormalize selectively under load (based on profiling, not upfront)
  5. Indexes — on WHERE, JOIN, ORDER BY fields
