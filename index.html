01 Node.js / Backend

package.json

Манифест проекта. Три ключевые роли: зависимости (dependencies — прод, devDependencies — только разработка), скрипты (scripts — точки входа: start, build, test, lint), метаданные (версия, имя, engines — минимальная версия Node).

package-lock.json — фиксирует точные версии всего дерева зависимостей для воспроизводимых сборок.

package.json

Project manifest. Three key roles: dependencies (dependencies — prod, devDependencies — dev only), scripts (scripts — entry points: start, build, test, lint), metadata (version, name, engines — minimum Node version).

package-lock.json — locks exact versions of the entire dependency tree for reproducible builds.

Event Loop

Event loop — механизм, позволяющий однопоточному Node.js делать неблокирующий I/O.

Алгоритм работы Event Loop:

  1. Берёт и выполняет весь синхронный код из Call Stack
  2. Проверяет очередь микротасков — если есть, выполняет все до единого
  3. Берёт одну задачу из очереди макротасков и выполняет
  4. Возвращается к шагу 2 (снова проверяет микротаски)
  5. Цикл повторяется пока есть задачи

Event Loop

Event loop — a mechanism that allows single-threaded Node.js to perform non-blocking I/O.

Event Loop algorithm:

  1. Takes and executes all synchronous code from the Call Stack
  2. Checks the microtask queue — if any, executes all of them
  3. Takes one task from the macrotask queue and executes it
  4. Returns to step 2 (checks microtasks again)
  5. The cycle repeats while there are tasks

Порядок выполнения кода

1) Синхронный код (Call Stack) — выполняется немедленно

console.log('Hi');
let a = 5 + 1;
function foo() {}

2) Microtasks — выполняются сразу после синхронного кода (и после каждого макротаска)

  • process.nextTick() — высший приоритет среди микро
  • Promise.then / catch / finally
  • queueMicrotask()

3) Macrotasks — берутся по одной, между ними всегда проверяются микротаски

  • setTimeout / setInterval
  • setImmediate (в Node.js)
  • I/O операции (файл, сеть)
  • UI рендеринг

Code execution order

1) Synchronous code (Call Stack) — executed immediately

console.log('Hi');
let a = 5 + 1;
function foo() {}

2) Microtasks — executed right after synchronous code (and after each macrotask)

  • process.nextTick() — highest priority among microtasks
  • Promise.then / catch / finally
  • queueMicrotask()

3) Macrotasks — taken one at a time, microtasks are always checked between them

  • setTimeout / setInterval
  • setImmediate (in Node.js)
  • I/O operations (file, network)
  • UI rendering

Нюансы Promise

Нюанс с Promise.resolve():
Promise.resolve() создаёт уже выполненный промис, но .then колбэк всё равно уходит в очередь микротасков — он не выполнится синхронно.

Promise.resolve().then(() => console.log('micro'));
// console.log('micro') — НЕ сразу, а после текущего синхронного кода

Нюанс с конструктором new Promise:
Колбэк внутри new Promise(executor) выполняется синхронно. Только .then уходит в микротаски.

console.log('1');                   // sync → 1
new Promise(resolve => {
  console.log('2');                 // sync → 2 (executor!)
  resolve();
}).then(() => console.log('3'));    // micro → 4
console.log('4');                   // sync → 3
// Вывод: 1, 2, 4, 3

Promise nuances

Promise.resolve() nuance:
Promise.resolve() creates an already resolved promise, but the .then callback still goes to the microtask queue — it won't execute synchronously.

Promise.resolve().then(() => console.log('micro'));
// console.log('micro') — NOT immediately, but after current synchronous code

new Promise constructor nuance:
The callback inside new Promise(executor) executes synchronously. Only .then goes to microtasks.

console.log('1');                   // sync → 1
new Promise(resolve => {
  console.log('2');                 // sync → 2 (executor!)
  resolve();
}).then(() => console.log('3'));    // micro → 4
console.log('4');                   // sync → 3
// Output: 1, 2, 4, 3

Полный пример

console.log('1');                   // sync → 1
setTimeout(() => console.log('2'), 0);  // macro → 5
setImmediate(() => console.log('3'));   // macro → 6
Promise.resolve().then(() =>
  console.log('4'));                // micro → 3
process.nextTick(() =>
  console.log('5'));                // micro (приоритет!) → 2
console.log('6');                   // sync → 4
// Вывод: 1, 6, 5, 4, 2, 3

setTimeout(() => ..., 0) — без задач выполняется последним из макро, потому что 0 ms ≠ немедленно, а «как можно скорее в фазе timers».

Full example

console.log('1');                   // sync → 1
setTimeout(() => console.log('2'), 0);  // macro → 5
setImmediate(() => console.log('3'));   // macro → 6
Promise.resolve().then(() =>
  console.log('4'));                // micro → 3
process.nextTick(() =>
  console.log('5'));                // micro (priority!) → 2
console.log('6');                   // sync → 4
// Output: 1, 6, 5, 4, 2, 3

setTimeout(() => ..., 0) — with no other tasks it runs last among macros, because 0 ms ≠ immediately, but rather "as soon as possible in the timers phase".

Асинхронность

Callback — функция, которую мы передаём в другую функцию как аргумент, чтобы она вызвала её позже (когда завершится операция). Это базовый механизм асинхронности в Node.js — «я закончу работу и вызову твою функцию с результатом».

fs.readFile('data.json', (err, data) => {
  // этот колбэк вызовется когда файл прочитан
});

Callback hell — вложенные колбэки, нечитаемо, сложно обработать ошибки:

getUser(id, (user) => {
  getOrders(user, (orders) => {
    getDetails(orders[0], (details) => { ... })
  })
})

Promise — объект, представляющий результат асинхронной операции, который будет доступен в будущем (или ошибку, если операция провалилась). По сути — «обещание» вернуть значение позже. Три состояния: pending (ожидание) → fulfilled (успех) / rejected (ошибка). Цепочка .then() линеаризует код, .catch() централизует обработку ошибок.

const promise = new Promise((resolve, reject) => {
  // асинхронная операция
  setTimeout(() => resolve('done'), 1000);
});

promise
  .then(result => console.log(result))  // 'done'
  .catch(err => console.error(err));

async/await — синтаксический сахар над Promise. async функция всегда возвращает Promise. await приостанавливает выполнение функции (не потока!) до резолва.

// Чисто, линейно, ошибки через try/catch
async function getOrderDetails(id) {
  const user = await getUser(id);
  const orders = await getOrders(user);
  return getDetails(orders[0]);
}

Параллельность: Promise.all([a(), b()]) — запускаем независимые задачи параллельно, а не последовательно через await.

Asynchrony

Callback — a function we pass into another function as an argument so it can call it later (when the operation completes). This is the foundational async mechanism in Node.js — "I'll finish my work and call your function with the result".

fs.readFile('data.json', (err, data) => {
  // this callback fires when the file is read
});

Callback hell — nested callbacks, unreadable, hard to handle errors:

getUser(id, (user) => {
  getOrders(user, (orders) => {
    getDetails(orders[0], (details) => { ... })
  })
})

Promise — an object representing the result of an asynchronous operation that will be available in the future (or an error if the operation failed). Essentially — a "promise" to return a value later. Three states: pending (waiting) → fulfilled (success) / rejected (error). Chaining .then() linearizes code, .catch() centralizes error handling.

const promise = new Promise((resolve, reject) => {
  // async operation
  setTimeout(() => resolve('done'), 1000);
});

promise
  .then(result => console.log(result))  // 'done'
  .catch(err => console.error(err));

async/await — syntactic sugar over Promises. An async function always returns a Promise. await pauses function execution (not the thread!) until resolution.

// Clean, linear, errors via try/catch
async function getOrderDetails(id) {
  const user = await getUser(id);
  const orders = await getOrders(user);
  return getDetails(orders[0]);
}

Concurrency: Promise.all([a(), b()]) — run independent tasks in parallel instead of sequentially via await.

02 React / Frontend

Компоненты

Функциональные — стандарт. Просто функция, возвращающая JSX. Состояние и сайд-эффекты через хуки (useState, useEffect, useMemo...).

Классовые — легаси. render(), lifecycle методы (componentDidMount, shouldComponentUpdate). Используются если проект старый или нужны Error Boundaries (хотя в React 19+ и это решается).

Как синьор: классы — только в legacy-коде. Новый код — только функциональные.

Components

Functional — the standard. Just a function returning JSX. State and side effects via hooks (useState, useEffect, useMemo...).

Class-based — legacy. render(), lifecycle methods (componentDidMount, shouldComponentUpdate). Used if the project is old or Error Boundaries are needed (though React 19+ addresses this too).

Senior take: classes — only in legacy code. New code — functional only.

Data flow — однонаправленный (unidirectional). Данные текут сверху вниз через props. Дочерний компонент влияет на родителя через callback-пропсы (родитель передаёт функцию, ребёнок вызывает).

Для глобального состояния: Context API (простое), Redux/Zustand (сложное).

Props vs State

PropsState
Incoming data from the parentComponent's internal data
Immutable for the receiverMutable via setter (setState / setX)
Unidirectional flow (top-down)Local, but can be "lifted up" (lift state up)

Data flow — unidirectional. Data flows top-down via props. A child component affects the parent through callback props (parent passes a function, child invokes it).

For global state: Context API (simple), Redux/Zustand (complex).

Controlled vs Uncontrolled

Controlled — React владеет значением инпута. Значение живёт в state, обновляется через onChange. Полный контроль: валидация на лету, условная логика, форматирование.

const [email, setEmail] = useState('');
<input value={email} onChange={e => setEmail(e.target.value)} />

Uncontrolled — DOM владеет значением. Читаем через ref когда нужно (например, при submit). Проще для простых форм, file inputs.

const ref = useRef();
<input ref={ref} />
// ref.current.value при submit

Как синьор: по умолчанию — controlled. Uncontrolled — только для file input или интеграции с non-React библиотеками.

Controlled vs Uncontrolled

Controlled — React owns the input value. The value lives in state, updated via onChange. Full control: on-the-fly validation, conditional logic, formatting.

const [email, setEmail] = useState('');
<input value={email} onChange={e => setEmail(e.target.value)} />

Uncontrolled — the DOM owns the value. Read via ref when needed (e.g., on submit). Simpler for basic forms, file inputs.

const ref = useRef();
<input ref={ref} />
// ref.current.value on submit

Senior take: controlled by default. Uncontrolled — only for file inputs or integration with non-React libraries.

03 TypeScript

Способы объявления типов

  • type — для union-типов, примитивов, утилит. type Status = 'active' | 'inactive'
  • interface — для объектов и классов. Поддерживает extends и declaration merging.
  • enum — набор констант. Предпочитаю as const объекты вместо enum (tree-shakeable).
  • Generics — параметризация: function get<T>(arr: T[]): T

Type declaration methods

  • type — for union types, primitives, utilities. type Status = 'active' | 'inactive'
  • interface — for objects and classes. Supports extends and declaration merging.
  • enum — a set of constants. I prefer as const objects instead of enums (tree-shakeable).
  • Generics — parameterization: function get<T>(arr: T[]): T

Почему TypeScript (не «потому что модно»)

  1. Safety — ошибки на этапе компиляции, а не в продакшене. Невозможно вызвать user.nmae — тайпчекер поймает.
  2. DX — автокомплит, рефакторинг с уверенностью (переименовал поле — IDE покажет все места), самодокументирующийся код.
  3. Масштабируемость — контракты между модулями/командами. Интерфейсы API-ответов, пропсов компонентов — всё типизировано, новый разработчик читает типы вместо документации.

Кратко: TypeScript — это инвестиция в поддерживаемость. На маленьком проекте overhead, на большом — спасает.

Why TypeScript (not "because it's trendy")

  1. Safety — errors caught at compile time, not in production. You can't call user.nmae — the type checker catches it.
  2. DX — autocomplete, confident refactoring (renamed a field — IDE shows every place), self-documenting code.
  3. Scalability — contracts between modules/teams. API response interfaces, component props — everything is typed, a new developer reads types instead of documentation.

In short: TypeScript is an investment in maintainability. Overhead on a small project, a lifesaver on a large one.

Iterators и Generators

Iterator — объект с методом __next__(). Лениво выдаёт элементы по одному. Любой for в Python работает через итераторы.

__next__() — метод, который возвращает следующий элемент из итератора. Когда элементы заканчиваются — выбрасывает исключение StopIteration. Цикл for вызывает этот метод автоматически и ловит StopIteration чтобы остановиться.

Generator — функция с yield вместо return. При вызове возвращает iterator, не выполняясь. Каждый next() выполняет код до следующего yield.

yield — ключевое слово, которое «отдаёт» значение вызывающему коду и замораживает функцию в текущем состоянии. При следующем вызове next() выполнение продолжается ровно с того места, где остановилось. В отличие от return, который завершает функцию навсегда, yield позволяет функции выдавать значения по одному.

def counter(n):
    i = 0
    while i < n:
        yield i      # отдаёт i и замирает
        i += 1       # продолжит отсюда при next()

gen = counter(3)
print(next(gen))     # 0
print(next(gen))     # 1
print(next(gen))     # 2
print(next(gen))     # StopIteration!
def read_huge_file(path):
    with open(path) as f:
        for line in f:
            yield line.strip()  # в памяти одна строка, не весь файл

Lazy evaluation — вычисляем значения только когда они нужны, а не все сразу.

Когда генераторы дают выигрыш:

  • Обработка больших файлов / потоков данных (не грузим всё в RAM)
  • Пайплайны трансформаций (цепочка генераторов = потоковая обработка)
  • Бесконечные последовательности (IDs, пагинация)
  • ETL-процессы где данные не помещаются в память

Iterators and Generators

Iterator — an object with a __next__() method. Lazily yields elements one by one. Every for loop in Python works through iterators.

__next__() — a method that returns the next element from the iterator. When elements run out — it raises a StopIteration exception. A for loop calls this method automatically and catches StopIteration to stop.

Generator — a function with yield instead of return. When called, it returns an iterator without executing. Each next() runs the code up to the next yield.

yield — a keyword that "hands off" a value to the caller and freezes the function in its current state. On the next next() call, execution resumes exactly where it left off. Unlike return, which terminates the function for good, yield lets the function produce values one at a time.

def counter(n):
    i = 0
    while i < n:
        yield i      # hands off i and freezes
        i += 1       # resumes here on next()

gen = counter(3)
print(next(gen))     # 0
print(next(gen))     # 1
print(next(gen))     # 2
print(next(gen))     # StopIteration!
def read_huge_file(path):
    with open(path) as f:
        for line in f:
            yield line.strip()  # one line in memory, not the whole file

Lazy evaluation — compute values only when they are needed, not all at once.

When generators give an advantage:

  • Processing large files / data streams (don't load everything into RAM)
  • Transformation pipelines (chain of generators = stream processing)
  • Infinite sequences (IDs, pagination)
  • ETL processes where data doesn't fit in memory

05 Коммуникация между сервисами / Service Communication

Sync vs Async

Синхронная (запрос-ответ)Асинхронная (очереди)
REST/gRPC — вызвал, ждёшь ответRabbitMQ, Kafka, SQS — отправил сообщение, не ждёшь
Когда нужен немедленный ответКогда ответ не нужен сразу
Простая отладка, но tight couplingLoose coupling, но сложнее дебажить

Когда что:

  • REST API — CRUD, получение данных для отображения, синхронные операции. Пользователь ждёт ответ.
  • Message queue — тяжёлые задачи (отправка email, генерация отчётов, обработка изображений), event-driven архитектура, когда сервис-потребитель может быть временно недоступен.

Пример из практики: На дашборде аналитики пользователь запрашивает отчёт по продажам за квартал — это REST, синхронно, потому что ему нужны данные прямо сейчас на экране. Но когда он нажимает «Экспорт в Excel» для 500k строк — мы кидаем задачу в очередь (Celery + Redis). Пользователь сразу видит «Отчёт формируется», а воркер в фоне генерирует файл и шлёт уведомление когда готово. Если бы мы делали экспорт синхронно — 30-секундный запрос убил бы и UX, и мог словить таймаут на nginx.

Правило: если ответ нужен на экран → sync. Если операция тяжёлая и пользователь может подождать отдельно → async.

Sync vs Async

Synchronous (request-response)Asynchronous (queues)
REST/gRPC — call and wait for a responseRabbitMQ, Kafka, SQS — send a message, don't wait
When an immediate response is neededWhen the response isn't needed right away
Easy to debug, but tight couplingLoose coupling, but harder to debug

When to use what:

  • REST API — CRUD, fetching data for display, synchronous operations. The user waits for a response.
  • Message queue — heavy tasks (sending email, report generation, image processing), event-driven architecture, when the consumer service may be temporarily unavailable.

From practice: On an analytics dashboard, a user requests a quarterly sales report — that's REST, synchronous, because they need the data on screen right now. But when they click "Export to Excel" for 500k rows — we push the task to a queue (Celery + Redis). The user immediately sees "Report is being generated", while a worker builds the file in the background and sends a notification when it's ready. If we did the export synchronously — a 30-second request would kill both UX and risk an nginx timeout.

Rule: if the response is needed on screen → sync. If the operation is heavy and the user can wait separately → async.

06 Дизайн БД / Database Design

Нормализация

Нормализация — процесс организации данных в БД таким образом, чтобы устранить избыточность (дублирование) и аномалии при вставке, обновлении и удалении данных. Суть: разбиваем одну большую таблицу на несколько связанных, где каждый факт хранится ровно один раз.

Цель — целостность данных. Если имя отдела хранится в одном месте (таблица departments), а не в каждой строке employees — переименование отдела = одна операция, а не обновление тысяч строк с риском рассинхрона.

Normalization

Normalization — the process of organizing data in a database to eliminate redundancy (duplication) and anomalies during inserts, updates, and deletes. The idea: split one large table into several related ones, where each fact is stored exactly once.

The goal is data integrity. If a department name is stored in one place (the departments table) rather than in every row of employees — renaming a department is a single operation, not updating thousands of rows with a risk of going out of sync.

Нормализация — уровни

Каждая следующая нормальная форма включает все предыдущие.

1NF — Атомарность
Каждая ячейка содержит одно значение, нет повторяющихся групп.
❌ phones: "+380..., +380..." — массив в одной ячейке
✅ Отдельная таблица user_phones с одной строкой на номер.

2NF — Нет частичных зависимостей
Каждый неключевой атрибут зависит от всего составного ключа, а не от его части.
Таблица order_items (order_id, product_id, product_name, quantity):
❌ product_name зависит только от product_id, а не от пары (order_id, product_id)
✅ Выносим product_name в таблицу products. В order_items оставляем только FK.

3NF — Нет транзитивных зависимостей
Неключевой атрибут не зависит от другого неключевого атрибута.
Таблица employees (id, department_id, department_name):
❌ department_name зависит от department_id, а не от id напрямую — транзитивная зависимость.
✅ Выносим department_name в таблицу departments.

BCNF (Бойса-Кодда) — ужесточение 3NF: каждый детерминант — кандидат в ключи. На практике редко отличается от 3NF, нужна только при нескольких перекрывающихся составных ключах.

4NF — нет многозначных зависимостей. Если сущность имеет два независимых набора связей (работник → навыки, работник → языки), они разносятся в отдельные таблицы. Иначе получаем комбинаторный взрыв строк.

На практике: доводим до 3NF — это стандарт для OLTP. Дальше (BCNF, 4NF) — только если видим конкретную аномалию. Потом точечно денормализуем под нагрузку.

Normalization — levels

Each successive normal form includes all the previous ones.

1NF — Atomicity
Each cell contains a single value, no repeating groups.
❌ phones: "+380..., +380..." — an array in a single cell
✅ A separate user_phones table with one row per number.

2NF — No partial dependencies
Every non-key attribute depends on the entire composite key, not just part of it.
Table order_items (order_id, product_id, product_name, quantity):
❌ product_name depends only on product_id, not on the pair (order_id, product_id)
✅ Move product_name to the products table. Keep only the FK in order_items.

3NF — No transitive dependencies
A non-key attribute does not depend on another non-key attribute.
Table employees (id, department_id, department_name):
❌ department_name depends on department_id, not directly on id — a transitive dependency.
✅ Move department_name to a departments table.

BCNF (Boyce-Codd) — a stricter version of 3NF: every determinant is a candidate key. In practice it rarely differs from 3NF, only needed with several overlapping composite keys.

4NF — no multi-valued dependencies. If an entity has two independent sets of relationships (employee → skills, employee → languages), they are split into separate tables. Otherwise you get a combinatorial explosion of rows.

In practice: normalize to 3NF — the OLTP standard. Beyond that (BCNF, 4NF) — only if you see a specific anomaly. Then selectively denormalize under load.

Денормализация

Намеренно дублируем данные для скорости чтения.

  • Плюсы: быстрые запросы без JOIN, проще агрегации
  • Минусы: дублирование, риск рассинхрона, сложнее обновлять
  • Типичные приёмы: добавить order_total в таблицу заказов (вместо SUM по items), хранить user_name рядом с комментарием, materialized views

Когда что: OLTP (транзакции) → нормализация. OLAP (аналитика, дашборды) → денормализация. На практике — гибрид.

Denormalization

Intentionally duplicate data for read speed.

  • Pros: fast queries without JOINs, simpler aggregations
  • Cons: duplication, risk of data going out of sync, harder to update
  • Common techniques: add order_total to the orders table (instead of SUM over items), store user_name alongside a comment, materialized views

When to use what: OLTP (transactions) → normalization. OLAP (analytics, dashboards) → denormalization. In practice — a hybrid.

Связи

  • 1:1 — user ↔ profile (редко, обычно для разделения горячих/холодных данных)
  • 1:N — user → orders (FK в таблице orders)
  • M:N — products ↔ categories (через junction table product_categories)

Relationships

  • 1:1 — user ↔ profile (rare, usually for separating hot/cold data)
  • 1:N — user → orders (FK in the orders table)
  • M:N — products ↔ categories (via a junction table product_categories)

Проектирование — подход

  1. Определить сущности и их атрибуты
  2. Определить связи и кардинальность
  3. Нормализовать до 3NF
  4. Денормализовать точечно под нагрузку (по результатам профилирования, не заранее)
  5. Индексы — на поля WHERE, JOIN, ORDER BY

Design approach

  1. Identify entities and their attributes
  2. Define relationships and cardinality
  3. Normalize to 3NF
  4. Denormalize selectively under load (based on profiling results, not upfront)
  5. Indexes — on WHERE, JOIN, ORDER BY fields
